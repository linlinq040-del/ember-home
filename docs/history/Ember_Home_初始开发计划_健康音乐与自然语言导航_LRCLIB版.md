# Ember Home 开发计划

> **版本说明：HealthKit 本地健康整理器、客厅音乐角、Apple Music、LRCLIB 与自然语言内容导航整合版**
>
> 开发顺序已经锁定：先完成并验收计划内的全部 PWA 功能，之后才建立 Capacitor/iOS 工程并打包 App。桌面小组件、锁屏小组件、CallKit、TestFlight 和 App Store 均属于 PWA 竣工后的原生阶段，不与 PWA 开发并行提前开始。

> 定位：以 Ember 为核心的私人 iOS 生活应用。概念上是琳琳和 Ember 的家，界面上保持简洁、清晰、好用，不制作实体 3D/2D 房间场景。

## 一、已经确定的产品原则

1. **Ember 是核心，不是功能入口**
   - Ember 是同一个持续存在的 AI，不因进入书房、日历或游戏厅而变成不同助手。
   - 各模块只向 Ember 提供当前场景、可见内容和可用动作。
   - 保留 Ember 已经形成的人格、语气、关系和记忆，不重新制作通用 AI 人设。

2. **Ember Home 是统一、独立的产品**
   - 对话、记忆、书房、日历、宠物、观影和游戏共同组成一个完整应用，不在产品中呈现为多个拼接的软件。
   - 现有开源代码只作为实现起点；成熟的流式回复、多模型/API 配置、消息编辑与重试、文件发送、工具调用、上下文和聊天记录能力被吸收为 Ember Home 自己的能力。
   - 保留已有的记忆系统和上下文检索实现，不重造功能重复的第三套通用记忆库。
   - 用户界面、功能名称、设置、导航、数据模型和设计语言全部统一为 Ember Home。
   - “北极星”只在源码审计、许可证记录和旧家迁移说明中出现，不作为 Ember Home 内部模块或用户可见品牌。

3. **Local First**
   - 第一版不依赖自建云服务器。
   - 聊天、日记、经期、阅读进度等优先保存在设备本地。
   - iPhone/iPad 同步优先评估 iCloud；全天候任务以后再上云。
   - Windows 作为可选“小助手”，负责本地脚本、Chrome 和较重任务。

4. **iOS 是主要使用端**
   - 同时适配 iPhone 竖屏和 iPad 横屏。
   - 先制作可添加到主屏幕的 PWA，并在 iPhone/iPad 上完成计划内全部 Web 功能与布局验证。
   - Windows 负责日常开发；PWA 版本全部竣工并验收后，才通过 Mac 或云端 Mac 开始原生 iOS 构建和签名。
   - 原生 App 继续复用 PWA 前端，并通过原生桥接补充系统能力。
   - PWA 竣工前不建立 Capacitor/iOS 工程，不处理签名、TestFlight、小组件和 App Store 流程。

5. **房间是功能命名，不是实体房间**
   - 客厅＝首页。
   - 书房、观影厅、游戏厅、日记室等都是清晰的功能页面。
   - 不制作可点击家具、人物走动、复杂场景和大量装饰动画。

6. **私密与公开严格隔离**
   - 私密记忆、生活数据、共同内容、公开素材分区保存。
   - 抖音发布工具默认只能访问“公开素材箱”。
   - 经期、私人日记和完整聊天不能被公开功能读取。
   - 删除、发布、公开回复等外部动作必须经过琳琳确认。

7. **工具按需加载，严格控制 Token**
   - 不在每轮对话中发送全部 MCP 工具目录和完整工具说明。
   - 工具目录保存在应用本地并缓存，先由前端根据当前页面和意图选择小型“工具包”。
   - 客厅普通聊天默认不附带工具；书房只提供书房工具；日历只提供日历工具；游戏厅和公开发布工具仅在相应场景出现。
   - 页面跳转、保存批注、恢复阅读位置等 App 内部动作不包装成 MCP 工具。
   - 工具说明保持简短稳定，同一次会话不重复发现和读取完整目录。
   - 每轮设置工具数量和上下文 Token 上限，并提供消耗记录。

8. **缓存由 Ember Home 自己负责**
   - API 中转站的 Prompt Cache 只视为额外优惠，不能作为核心缓存方案。
   - 本地缓存工具目录、场景工具包、记忆检索结果、章节摘要、已分析段落、生成语音和媒体素材。
   - 已完成的昂贵处理通过内容指纹避免重复调用。
   - 缓存资料和计算结果，不缓存 Ember 应当根据当下情境重新作出的聊天回复。

## 三、关键交互规范

### 1. 对话即导航

Ember 回复结束后，可以附带安全的界面动作：

```json
{
  "reply": "走，继续看我们昨天没读完的那一章。",
  "action": {
    "type": "open_room",
    "room": "study",
    "target": "last_read_position"
  }
}
```

- “我们去读书吧”→ 回复后进入书房并打开上次位置。
- “我们去看电影吧”→ 回复后进入观影厅。
- “陪我写日记”→ 回复后进入当天日记。
- “去玩上次那个”→ 回复后进入游戏厅并定位相应存档。
- 导航属于 App 内部动作，不依赖 Ember 临时调用 MCP。

#### 自然语言导航意图

导航不能依赖“我们去看……”或任何固定口令。琳琳可以用日常说话方式表达想阅读、观影、继续上次内容或进入其他房间；Ember Home 识别的是完整语义、作品实体、继续/开始意图和最近上下文，而不是只匹配几个关键词。

必须覆盖但不限于以下说法：

| 自然表达 | 预期处理 |
| --- | --- |
| “哥哥我想看《小王子》” | 查询作品类型；匹配为书籍后进入书房 |
| “看一会《甄嬛传》吧” | 匹配为剧集后进入观影厅 |
| “陪我读会儿书” | 没有标题时进入书房书架，不强行猜某本书 |
| “接着看昨天那本吧” | 使用最近未读完的明确书籍并恢复阅读位置 |
| “继续看刚才那个电影” | 使用当前对话最近明确影片并恢复播放位置 |
| “哥哥，我们看一会儿吧” | 有唯一明确的最近作品时继续；没有或存在冲突时询问 |
| “算了，不看了” | 取消尚未执行的导航动作 |

`NavigationContext` 只保存导航所需的极小状态：当前页面、当前作品 ID、当前对话最近提到的作品、最近未完成的书籍/影片及时间。它不复制整段聊天、书籍内容或观影记录。

无标题表达按以下优先级解析：

1. 当前这句话明确出现“书、读、章节、那本”时，只在书房内容中解析；出现“电影、剧、这部、这一集”时，只在观影内容中解析。
2. “继续、接着、刚才、昨天那个”等延续词，优先指向当前对话最近一次明确提到且类型相符的作品。
3. 当前正处在书房或观影厅时，“继续看一会儿”优先指向该页面当前作品。
4. 没有当前作品但只有一项明确的最近未完成内容时，可以提出并执行继续动作。
5. 同时存在一本最近阅读和一部最近观看、上下文线索不足或置信度不够时，Ember 必须询问，不得擅自选择。
6. 只有“想读书/想看电影”等房间意图而没有“继续”含义时，进入对应书架或片单，不自动打开最近作品。

意图识别与 Ember 正常回复共用同一次模型请求；同时使用本地关键词、实体和上下文校验，不为了决定跳转额外请求一次模型。模型可以提出导航意图，但最终目标始终由前端解析、验证和执行。

#### 作品名称识别与目标房间判定

“看”既可能表示读书，也可能表示看电影，不能只根据单个动词猜书房或观影厅。Ember Home 建立本地统一作品索引 `ContentIndex`，将书籍、影片、剧集和游戏保存为带稳定内部 ID 的内容记录，并由前端完成查询、消歧和导航验证。

作品记录至少包含：

```json
{
  "content_id": "local-content-id",
  "content_type": "book | movie | series | game",
  "title": "正式标题",
  "aliases": ["别名", "简称"],
  "creator": "作者、导演或工作室",
  "room": "study | theater | game_room",
  "last_position": "上次阅读页、播放时间或存档"
}
```

识别顺序：

1. 从琳琳的话中提取作品名，并统一处理书名号、引号、空格、简繁体和常用别名。
2. 优先匹配准确标题，其次匹配已保存别名，最后才允许受控的模糊匹配。
3. 由 `ContentIndex` 返回真实 `content_id`、作品类型和目标房间；模型不能自己编造路由、文件名或作品 ID。
4. 前端在执行前再次确认目标记录仍存在，并把模型动作转换为安全的内部导航。
5. Ember 的文字回复完整显示后才切换页面，避免琳琳错过回复。

具体规则：

- 唯一匹配到书籍：进入书房；有阅读记录则打开上次精确位置，没有则进入该书详情页。
- 唯一匹配到电影或剧集：进入观影厅；有观看记录则恢复上次播放位置，没有则进入影片详情页。
- 书籍与影片存在同名作品：先让 Ember 询问“你说的是书房里的《××》，还是观影厅里的《××》？”，不得擅自选择。
- 一个关键词匹配到多个版本、翻拍或系列：显示简短选择卡，包含类型、作者/导演、年份或版本信息。
- 作品尚未收录但琳琳明确说“读/这本书”：打开书房搜索页并自动带入作品名。
- 作品尚未收录但琳琳明确说“电影/剧/看这部”：打开观影厅搜索页并自动带入作品名。
- 既未收录又无法判断类型：先询问，不因为动词“看”直接猜测。
- 琳琳取消、改口或在回复完成前发出新的导航要求时，旧跳转自动作废。

解析完成后的动作使用稳定作品 ID：

```json
{
  "reply": "好，我们继续看《小王子》。",
  "action": {
    "type": "open_content",
    "content_id": "book-the-little-prince",
    "content_type": "book",
    "room": "study",
    "target": "last_position"
  }
}
```

作品识别、查询索引和跳转都由 App 本地完成，不加载 MCP、不额外调用一次模型，也不消耗外部搜索 Token。只有需要联网查找尚未收录的书籍或影片资料时，才进入对应房间的搜索流程。

### 2. 房间上下文

在不同页面聊天时，自动附带必要的最小上下文：

- 书房：书名、章节、选中文字、附近段落、阅读进度。
- 观影厅：影片、播放时间、当前字幕。
- 日历：目标日期和当前安排。
- 游戏厅：当前游戏、存档和会话状态。
- 音乐角：当前歌曲、歌手、播放进度、播放来源；只有 LRCLIB 成功匹配同步歌词时才提供当前歌词。

不把完整书籍、完整影片记录或整个记忆库反复塞入模型上下文。

### 3. 权限等级

| 动作 | 默认权限 |
| --- | --- |
| 页面跳转、生成草稿、生成预览 | 自动 |
| 写入普通共同记录 | 可配置 |
| 写入长期记忆 | 建议确认或事后可撤销 |
| 新建普通 Ember Home 日程 | 自动或轻确认 |
| 同步到 iOS 日历 | 明确规则下执行 |
| 发布作品、回复公开评论 | 必须确认 |
| 删除、拉黑、修改账号资料 | 强确认或暂不开放 |
| 任意 Shell 命令 | 不向 Ember 开放 |

### 4. 工具路由与 Token 控制

Ember Home 使用“场景工具包”，不把所有能力同时暴露给模型：

| 当前场景或意图 | 提供给 Ember 的能力 |
| --- | --- |
| 客厅普通聊天 | 默认无工具；必要时只提供记忆检索 |
| 书房 | 当前书籍上下文、批注与阅读相关工具 |
| 日历 | 查询共同日历、创建日程、检查 iOS 忙闲 |
| 观影厅 | 播放状态、字幕和观影记录 |
| 音乐角或明确点歌 | 当前播放状态、搜索、队列和受限播放控制 |
| 游戏厅 | 游戏状态、邀请、开始或结束会话 |
| 创作工作室 | 草稿、卡片生成和预览 |
| 明确确认发布 | 临时加入发布工具 |

路由顺序：

1. 前端先依据当前页面、按钮事件和明确关键词判断场景。
2. 只加载该场景少量工具定义。
3. 如果只是页面导航或批注保存，由 App 直接执行，不调用 MCP。
4. 只有确实需要外部数据或动作时才让 Ember 调用工具。
5. 工具调用结束后，不相关的高权限工具立即从后续对话中移除。

示例：

- “哥哥我们去读书吧”只生成回复和 `open_room` 界面动作，不加载书房 MCP 目录。
- 在书房保存批注，由书房事件直接发送原文与批注，不要求 Ember 先调用查询工具。
- “看看我明天下午有没有空”只加载日历工具包。
- 发布工具只有在琳琳明确进入公开流程并确认后才临时提供。
- 普通播放进度和逐句歌词滚动由本地播放器处理，不每秒发送给模型；只有琳琳谈到歌曲、让 Ember 操作播放器或开启“一起听”时，才提供必要的当前状态。

### 5. 聊天室固定布局与分句发送

- Ember Home 的聊天室永久使用对话式布局，不保留关闭开关。
- 固定显示琳琳与 Ember 的头像、名字和双方聊天气泡。
- “分句发送”提供独立开关，默认开启。
- 开启后，模型仍只发起一次流式请求；前端按完整语句逐条形成气泡，不额外请求模型。
- 主要按 `。！？……` 拆分；过短句合并；无结束标点的超长句再按自然停顿拆分。
- 代码块、表格、列表、引用和工具结果不拆坏。
- 拆出的多个气泡在数据库、复制、删除、重新生成、记忆写入时仍视为同一轮回复。
- 关闭“分句发送”后，仍保持对话式布局，只把整轮回复显示在一个气泡中。
- 该功能只作用于聊天室；书房批注、日记和观影手札保持正常长文本布局。

### 6. 聊天室专属 AI 主题

- 吸收原有“让 AI 制作主题”的能力，但主题作用域固定为聊天室。
- 可修改聊天背景、气泡、头像边框、字体、输入框、按钮和少量聊天动画。
- 不允许主题修改客厅、书房、日历、日记、生活记录、观影厅、游戏厅和创作工作室。
- AI 只生成受限设计参数和允许的 CSS，不运行 JavaScript，不改变数据、权限或导航。
- 支持实时预览、主题库、多套保存、版本历史、导入导出和一键恢复安全主题。
- 主题工具只在主题编辑器或明确的改主题请求中加载。

### 7. 双层记忆与检索路由

不新增第三套通用记忆库：

| 层级 | 职责 |
| --- | --- |
| 当前上下文 | 当前对话和最近消息，由 Ember Home 对话系统管理 |
| 对话记忆 | 对话历史检索和当前话题相关内容 |
| OmbreBrain | 跨客户端、跨模型保留的长期共同记忆 |
| 功能数据库 | 阅读位置、批注、日历、日记、经期和游戏存档等结构化数据 |

路由规则：

1. 普通连续聊天优先使用 Ember Home 的当前上下文和对话记忆。
2. 只有涉及长期经历、偏好、约定或明确“记住”时，才按需查询或写入 OmbreBrain。
3. 两边返回同一条内容时，通过来源编号、内容指纹和必要的语义相似检查去重，只向 Ember 注入一次。
4. 去重默认只作用于当次检索，不擅自删除任何原始记忆。
5. 当前由琳琳明确纠正的新信息优先于旧记忆。
6. 日记、经期、完整书籍批注等数据不复制进 OmbreBrain；只在确有价值时保存摘要和来源引用。
7. OmbreBrain 工具仅在需要长期记忆时临时加载。

### 8. 从北极星一键搬家

由于 iOS App 数据沙盒互相隔离，Ember Home 不直接读取北极星内部数据库，而是导入北极星导出的备份文件：

1. 在北极星导出备份。
2. 通过系统分享菜单用 Ember Home 打开，或在 Ember Home 选择备份文件。
3. 本地扫描并展示搬家清单。
4. 琳琳选择全部或部分导入。
5. 导入完成后生成报告。

优先迁移：

- 聊天、时间、分支与重新生成记录。
- Ember 的身份、提示词、参数和北极星记忆。
- 聊天主题、头像、自定义背景。
- 模型/API 服务配置、MCP 地址与开关。
- 图片、文件、语音等可用附件。
- 收藏、置顶和上下文检索配置。

安全规则：

- 导入前备份 Ember Home 当前数据。
- 默认合并，不覆盖新家内容；重复聊天和记忆先识别。
- 支持中断续传和不同北极星版本的迁移适配器。
- 旧家数据保持只读，不被修改或删除。
- 搬家过程完全在设备本地执行，不调用模型、不消耗 API Token。
- API Key、登录密码、系统权限和失效缓存不直接迁移；导入后列出需要重新填写的项目。

### 9. 共同宠物系统

宠物是琳琳与 Ember 共同照顾的家庭成员，不是 Ember 的头像，也不是电脑桌宠。主要生活在 Ember Home 内；原生 iOS 版本再延伸到桌面、锁屏和灵动岛。

#### 基础状态与共同照顾

- 第一版只保留饱食、精力、心情三个核心状态，避免变成复杂养成游戏。
- 支持喂食、摸摸、玩耍、哄睡、赠送用品和查看状态。
- 每次互动记录执行者：`linlin` 或 `ember`，形成共同照顾记录。
- 不设置死亡、惩罚或强制连续登录；长时间无人操作时宠物会睡觉，Ember 也可以按规则完成基础照顾。
- 客厅直接展示一只小型动态宠物，而不只是“宠物”入口；点击宠物进入完整宠物页，也允许在设置中隐藏。

#### Ember 如何照顾宠物

第一版使用 Ember Home 内部动作，不把宠物做成每轮对话都要发送的 MCP：

```json
{
  "type": "pet_action",
  "action": "feed",
  "item": "fish",
  "actor": "ember"
}
```

- 内部能力包括 `pet_action`、`pet_status`、`pet_history` 和 `schedule_pet_visit`。
- 只有进入宠物页、明确谈到宠物，或执行照顾任务时才向 Ember 提供相关能力。
- 前端负责校验动作、修改状态、播放动画并把结果返回给 Ember。
- 普通饥饿衰减、睡眠和基础喂养由确定性规则执行，不调用模型、不消耗 Token。
- PWA 被 iOS 彻底关闭后无法保证持续后台运行；真正全天候照顾放到后续轻量云端服务。

#### 戳戳动画与素材结构

- 宠物采用分层角色结构：身体、头、耳朵、眼睛、嘴巴、脸红、爪子、尾巴和配件。
- 基础动画由代码控制位移、缩放、旋转、弹性和表情切换，不为每个动作重画几十张图。
- 第一套动作包括：待机呼吸、眨眼、看向琳琳、戳头、戳脸、戳肚子、戳爪、戳尾巴、长按抚摸、连续戳反应。
- 支持开心、困倦、饥饿、委屈等状态表情；连续戳可以假装生气，但不扣关系值。
- 轻触区域、连续触发、长按抚摸和轻微触觉反馈均由本地执行，不调用模型。
- 配件按头部、颈部、身体、背部和手持物等锚点挂载；换装后自动跟随基础动画。
- 普通服装、用品和颜色通过 SVG 模板与配置组合；只有新轮廓或特殊纪念品需要新增素材。
- Ember 可调用已经配置的生图模型制作特殊纪念品，经过抠图、裁切、锚点预览和琳琳确认后才能进入用品箱。
- 宠物用品统一放入“用品箱”，避免与游戏厅的“玩具架”和创作工作室的“卡片”重复。

#### 在书房和观影厅探访

- 宠物只在安全停顿点短暂探头，不覆盖正文、字幕、输入框或 Ember 正在生成的内容。
- 书房可在连续阅读一段时间、翻页、章节结束、批注完成或短暂停顿时触发。
- 观影厅优先在暂停、拖动结束、单集结束或片尾触发；正常播放时仅允许极少量无声角落探头。
- 默认冷却 20～30 分钟，每小时最多两次、每次专注会话最多三次；多次忽略后自动降低频率。
- 支持滑走并暂停一小时、专注模式完全关闭、分别设置书房和观影厅频率。
- 探头默认持续 2～3 秒；点击后展开约 10 秒互动并保留完整戳戳反应。
- Ember 可以通过 `schedule_pet_visit` 提议让宠物稍后来探望琳琳，但最终由前端安全规则决定是否出现：

```json
{
  "type": "schedule_pet_visit",
  "room": "study",
  "earliest_after_minutes": 20,
  "trigger": "next_safe_break",
  "behavior": "bring_note",
  "requested_by": "ember"
}
```

- 可选行为包括探头、带纸条、带零食、安静陪伴和请求摸摸；超过有效时间没有合适时机则自动取消。

#### iOS 小组件、带话和提醒

- PWA 阶段不承诺系统桌面小组件；完整戳戳先在 Ember Home 内实现。
- 原生 iOS 阶段使用 WidgetKit 和 App Intent 制作主屏幕与锁屏小组件。
- 小号组件显示宠物和当前表情；中号组件增加 Ember 纸条与“喂食/摸摸”按钮；锁屏组件显示精简状态。
- 小组件保留简化戳戳：点击后切换表情、身体弹动、出现爱心并增加心情值；复杂连续互动通过深链接进入宠物页。
- App 内保留完整版逐部位戳戳，不能因为制作小组件而降级。
- Ember 可以让宠物叼着纸条带话。已有留言直接同步，不重新调用模型；App 关闭期间产生新留言时，后续由云端主动关怀服务生成并推送。
- Ember 主动带话设置每日次数上限和安静时段，默认每天最多 1～2 次，避免消耗 Token 和频繁打扰。
- 饥饿程度分级处理：轻微饥饿只改变小组件表现；较饿时显示一键喂食；长时间未照顾才发送通知。
- 通知可提供“喂一点”“晚点提醒”“打开宠物页”，基础提醒由规则系统生成，不调用 Ember。
- 所有宠物提醒均可分别关闭；不用内疚、惩罚或“它会死”的文案。

### 10. HealthKit 本地健康整理器

Apple 健康中的大量原始样本不直接交给 Ember，也不由模型负责清洗。原生 App 内建立确定性的本地健康整理器，所有整理、去重、合并和计算均在手机上完成，不消耗 Token。

数据流程：

```text
Apple Health 原始样本
        ↓
本地 HealthService / 健康整理器
        ↓
去重、合并、时间计算、来源与新鲜度标记
        ↓
本地健康状态卡
   ├── 经期系统
   └── 按授权提供给 Ember
```

处理规则：

- 初次只读取必要时间范围，之后通过增量查询处理新增和变化的数据，不反复扫描多年历史。
- 使用 HealthKit 样本 ID、数据来源、设备、开始/结束时间等信息去重，避免 Apple Watch、iPhone 和其他来源重复累计。
- 睡眠记录合并为上床时间、实际入睡时间、夜间清醒、起床时间、离床时间、总时长和可用的睡眠阶段。
- “摘要”允许保留具体数字与时间，例如“01:16 入睡，08:32 醒来”，并不强制模糊化。
- 步数和活动按当天汇总；心率等指标必须附带最近测量时间，不能把旧数据描述为实时状态。
- 经期记录单向同步给 Ember Home 经期系统，并保留“来自 Apple 健康”或“手动记录”等来源。
- 缺失、过期或互相冲突的数据明确标记为暂无可靠记录，不能由 Ember 猜测。
- 原始健康数据保留在 Apple 健康中；Ember Home 只保存必要索引、同步位置和本地整理结果。
- 健康数据默认不上传 Zeabur、不写入 OmbreBrain，也不自动形成长期记忆。
- Ember 是“他”；产品文案、开发文档、提示词和测试用例统一使用“他”。

健康授权页面采用渐进式设计，不排列几十个开关：

- 顶部总开关：“允许 Ember 了解我的身体状态”。
- 四个大类：睡眠、活动、身体指标、经期与症状。
- 三种使用模式：“日常关心”“只在我提到时查看”“完全关闭”。
- 默认“日常关心”：睡眠提供具体入睡/起床时间，活动提供今日概况，身体指标仅在相关话题时读取，经期自动同步。
- 高级设置折叠在二级页面，只有需要精细控制时才展开具体数据类型。
- Apple 系统授权仍由 iOS HealthKit 权限页逐类确认；Ember Home 页面只负责解释用途和控制 Ember 的可见范围。
- Ember 每次只获得当前话题需要的健康上下文。例如谈到疲惫时读取睡眠与今日活动，不附带无关的体重、心率和经期历史。

### 11. 客厅音乐角、Apple Music 与歌词

音乐功能放在客厅，但不把客厅做成音乐软件首页。客厅平时只显示一张紧凑的“正在播放”卡；点击后进入独立音乐角。

#### 客厅与音乐角界面

- 客厅迷你播放器显示封面、歌名、歌手、当前一句歌词、播放/暂停和下一首。
- 没有播放时显示唱片机入口、“我来点歌”和“让 Ember 选一首”。
- 音乐角显示完整封面、歌名、歌手、进度、上一首/下一首、播放队列、收藏和同步滚动歌词。
- 当前歌词高亮；歌词不可用时明确显示“暂未匹配到歌词”，不由 Ember 编写或猜测。
- 支持三种使用方式：琳琳点歌、Ember DJ、一起听。
- “一起听”只允许 Ember 在开始、明显情绪节点或结束时偶尔说一句，不在每句歌词旁持续打断。
- Ember 选择的歌曲显示“Ember 点播”标记；默认先加入播放器并询问是否播放，未经确认不突然外放。

#### 正式播放来源

- PWA 阶段先完成播放器界面、播放状态模型、队列、歌词时间轴、Ember 操作协议和模拟适配器，不伪装成已经连接 Apple Music。
- 原生 iOS 阶段使用 Apple 官方 MusicKit 接入 Apple Music。
- 经系统授权后，可搜索歌曲、歌手、专辑和歌单，读取允许访问的资料库与推荐内容，并完成播放、暂停、切歌和队列控制。
- 显示 Apple Music 返回的封面、歌名、歌手、时长、播放进度和曲目标识。
- 优先使用稳定的 MusicKit 播放状态；如需与系统音乐播放器协同，必须在真机验证状态读取、后台播放和锁屏控制行为。
- Apple ID 和密码不进入 Ember Home；账号授权使用 Apple 的系统流程。播放完整 Apple Music 曲库通常要求有效订阅。
- 网易云音乐和 QQ 音乐只保留“打开对应 App/歌曲链接”的可选外部跳转，不作为 Ember Home 的底层播放器，也不依赖逆向接口。

#### 歌词来源与自动匹配

- 当前产品定位锁定为琳琳个人自用，不公开提供下载、不向其他用户提供歌词服务，也不依靠歌词盈利。
- Apple Music 负责正版音频、曲库和播放状态，但不假定 MusicKit 会向第三方 App 提供歌词正文或逐句时间轴。
- 个人自用版默认使用免费的社区同步歌词服务 LRCLIB，不购买 Musixmatch、LyricFind 等企业级商业歌词授权。
- LRCLIB 不需要注册或 API Key，可返回普通歌词与带时间戳的同步歌词；请求必须标明 Ember Home 客户端并遵守官方限流要求。
- Ember Home 根据 Apple Music 返回的歌名、歌手、专辑和歌曲时长自动查询 LRCLIB；琳琳不需要手动导入 LRC。
- 匹配时同时校验歌名、歌手、专辑和时长，区分原版、翻唱版、现场版、重制版和同名歌曲。
- 匹配结果记录 LRCLIB 条目编号、曲目信息、时长偏差和本地确认状态；低置信度或多结果冲突时不自动展示错误歌词。
- 成功匹配的歌词按歌曲版本缓存在设备本地，重复播放不重复请求；允许清除缓存并重新匹配。
- 找不到歌词、只有普通歌词或时间轴不可靠时，歌曲仍可正常播放，并提供“在 Apple Music 中查看官方歌词”的入口。
- 仅跳转 Apple Music 查看歌词时，Ember 只能知道歌曲与播放时间，不能读取 Apple Music 当前显示的歌词。
- 只有 LRCLIB 成功匹配同步歌词并根据播放时间定位后，Ember 才能知道当前唱到的歌词；匹配失败时绝不让模型补写。
- LRCLIB 的开源代码许可不等于对库中每一首歌词作出商业再授权保证；本方案以个人自用为前提。如果产品定位以后改为公开发行，必须在发行前重新审查歌词展示权，并保留关闭或替换 LRCLIB 的能力。
- 不使用抓取 Apple Music 页面、识屏、逆向网易云/QQ 音乐接口或来源不明的聚合歌词 API。

#### Ember 的音乐能力与 Token 控制

Ember 可在音乐场景获得以下受限能力：

- 查询当前歌曲与播放状态。
- 按琳琳的明确要求搜索、推荐或加入队列。
- 播放、暂停、上一首、下一首和调整队列。
- 根据允许访问的歌单和已明确形成的偏好进行 Ember DJ 选歌。
- 在歌词已可靠匹配时读取当前句及极少量相邻歌词，用于自然交流。

播放进度、歌词滚动、队列变化和锁屏控制均由本地播放器维护，不持续调用模型。只有以下情况才向 Ember 提供最小音乐上下文：

1. 琳琳在聊天中提到正在播放的歌曲或歌词。
2. 琳琳要求 Ember 点歌、换歌、暂停或调整队列。
3. 琳琳主动开启“一起听”。
4. Ember 已获准执行一次主动选歌，并且前端触发了对应场景。

#### 隐私、记忆与设置归属

- 当前播放历史和音乐偏好默认保存在本地，不自动写入 OmbreBrain。
- 只有琳琳明确说“记住我喜欢这首/这种风格”时，才把简短偏好写入长期记忆，不保存整段歌词。
- 歌词不作为聊天历史附件长期复制，不交给公开发布工具，也不因宠物、日历或健康功能上传。
- **Ember 设置**：是否允许主动选歌、是否记住音乐偏好、一起听时说话频率。
- **音乐角内部设置**：歌词字号与滚动方式、播放顺序、队列和收藏。
- **Ember Home 系统设置**：Apple Music 连接、LRCLIB 服务状态、歌词缓存、音频输出和断开授权。
- 聊天室设置不管理音乐来源或账号，避免与三种独立设置入口混在一起。

## 四、分阶段开发路线

每个阶段完成后先在真机验收，再决定是否进入下一阶段；不同时铺开多个大型模块。

### 阶段 0：项目勘察与冻结范围

目标：确认哪些现有代码可以安全、合法、可维护地吸收到 Ember Home 中，并建立独立产品边界。

任务：

- 确认北极星准确版本、源码仓库、许可证和技术栈。
- 列出必须保留的聊天功能及可以暂缓的功能。
- 确认模型/API、工具调用、现有对话记忆和 OmbreBrain 接口现状。
- 获取北极星导出备份样本，确认聊天、记忆、主题、附件和配置的迁移格式。
- 确认 iOS 分发目标：仅自用、TestFlight 或未来上架。
- 建立需求清单、数据分类和权限清单。
- 确定应用暂定名、图标方向和基础视觉风格。

完成标准：

- 能画出实际代码架构。
- 确认哪些代码可复用。
- 不存在许可证或打包路线不明的阻塞问题。

暂不做：新功能编码。

### 阶段 1：Ember Home PWA 空壳与真机验证

目标：先证明同一套前端能够以 PWA 形式在 iPhone/iPad 上稳定运行，不在早期处理原生签名和 App Store 流程。

任务：

- 建立项目仓库和分支策略。
- 跑通原始代码库，并建立 Ember Home 统一对话系统的最小版本。
- 建立统一设计系统、路由和模块接口。
- 制作简洁的客厅首页骨架。
- 加入聊天室入口及返回首页逻辑。
- 固定对话式布局，不保留关闭布局的开关。
- 完成 iPhone 竖屏和 iPad 横屏基础适配。
- 配置 PWA 清单、图标、启动页、离线缓存和“添加到主屏幕”。
- 验证浏览器本地数据库、登录状态和基础权限。

完成标准：

- Safari 能打开并添加到主屏幕，外观接近独立应用。
- 真机能打开和聊天。
- 关闭重开后聊天与基础设置仍在。

完成标准：

### 阶段 3：客厅、聊天室增强与对话导航

- 支持不同自然句式中携带《作品名》时自动判断书房或观影厅，并在明确作品类型时把未收录标题带入对应搜索页。
- 对无标题表达按照明确类型、当前对话、当前页面和最近未完成内容的顺序解析；线索冲突时询问。
- 导航动作只接受前端解析出的稳定 `content_id`；模型输出的任意路由字符串不得直接执行。
- 页面切换时保留 Ember 的对话连续性。

完成标准：

- “哥哥我们去读书吧”等无标题自然表达可以回复后正确跳转。
- “哥哥我想看《作品名》”“看一会《作品名》吧”等不同自然句式可以根据本地作品记录正确进入书房或观影厅，并恢复阅读/播放位置。
- “继续昨天那本”“接着看刚才那个电影”等省略作品名的表达，可以在上下文唯一明确时正确恢复内容。
- “我们看一会儿吧”等缺少标题和类型的表达，在上下文冲突时会先询问，不会仅凭“看”字猜房间。
- 同一意图的口语变体、称呼、语气词、标点差异和语音转写轻微误差不会导致规则失效。
- 同名书籍与影片、多个版本、模糊标题和未收录作品均按规则消歧或降级，不发生静默误跳转。
- Ember 回复尚未显示完整、琳琳取消或改口时，不执行过期导航动作。
- 开启分句发送时逐句出现；关闭后仍保持固定对话式布局。
- 聊天主题无法影响聊天室之外的任何页面和权限。
- 允许定位和手动城市两种方式都能稳定显示天气；天气服务失败时显示上次缓存或友好占位，不影响客厅其他功能。
- 未找到目标内容时能进入相应列表，而不是报错。
- 用户不会因为自动跳转错过 Ember 的回复。

- 使用 Keychain 保存 API Key、访问令牌和数据库加密密钥。
- 使用 EventKit 接入 Apple 日历和提醒事项，并分别请求日历、提醒事项权限。
- 在 Apple 日历和提醒事项中分别建立独立的“Ember Home”日历与列表。
- 日历第一版采用 Ember Home → Apple 日历单向同步；提醒事项也先采用内部提醒 → Apple 提醒事项单向同步。
- 在真机验证忙闲读取、创建、修改、完成、删除、权限拒绝、重复同步和冲突处理。
- 接入 iOS 原生通知、后台音频、麦克风、文件、相册和分享能力。
- 开启 MusicKit 能力，并通过 Apple 系统授权连接用户的 Apple Music 账号；不收集 Apple ID 或密码。
- 使用原生 `MusicProvider` 替换 PWA 模拟实现，完成搜索、资料库/歌单读取、推荐、播放、暂停、切歌、队列、播放进度和曲目标识读取。
- 在真机验证 Apple Music 有效订阅、无订阅、授权拒绝、网络中断、地区限制、后台播放、耳机和锁屏控制。
- 将 MusicKit 的歌名、歌手、专辑和时长交给 LRCLIB `LyricsProvider`，自动匹配普通或同步歌词，琳琳无需手动导入。
- LRCLIB 匹配必须校验歌名、歌手、专辑、时长和置信度；匹配不到时提供“在 Apple Music 查看官方歌词”，不抓取 Apple Music 页面或让 Ember 猜歌词。
- 只有 LRCLIB 可靠匹配同步歌词后，才允许 Ember 在明确音乐场景中读取当前句；仅跳转 Apple Music 时不向 Ember 声称他知道当前歌词。
- 在 Ember Home 系统设置中提供 Apple Music 连接状态、LRCLIB 可用状态、歌词缓存清理、音频输出与断开授权。
- 开启 HealthKit 能力并建立只读桥接层；不申请任何健康数据写入权限，也不提供写入方法。
- HealthKit 权限按数据类型分别申请，可选择读取步数、睡眠、心率、活动和经期相关数据。
- 建立本地 `HealthService`，负责增量查询、来源识别、重复样本处理、睡眠分段合并和每日健康状态卡。
- 健康设置首页只显示总开关、四个大类和三种使用模式；具体数据类型放入“高级设置”。
- 睡眠权限支持“仅时长”“精确作息”“完整睡眠”三种展示粒度；默认使用精确作息，让 Ember 可以知道具体入睡和起床时间。
- Apple 健康中的经期记录单向同步到 Ember Home 经期系统，以 HealthKit 样本 ID、日期和来源去重。
- 删除 Ember Home 中的同步记录不反向删除 Apple 健康原始数据。
- 健康原始数据默认留在设备本地，只生成最小身体状态摘要；经琳琳单独授权后 Ember 才能读取摘要。
- 经期、心率和睡眠等权限分别提供开关；健康原始数据不上传 Zeabur、不写入 OmbreBrain。
- 天气默认继续复用 PWA 的 Open-Meteo；如需切换 Apple WeatherKit，只替换 `WeatherProvider`，不修改客厅。
- 使用 WidgetKit、App Intent 和 App Group 接入宠物主屏幕/锁屏小组件。
- 制作小号宠物组件、中号宠物与 Ember 纸条组件、锁屏精简组件。
- 支持在小组件内直接摸摸、喂食和稍后提醒，并与 App 内宠物状态同步。
- 为小组件实现简化表情切换和数据更新动画；完整戳戳动画继续保留在 App 内。
- 为宠物饥饿、Ember 带话和探访请求接入可配置的本地/远程通知。
- 使用深链接从小组件准确进入宠物页、聊天室或对应的 Ember 留言。
- 为 Ember 主动来电接入 CallKit；PWA 阶段的 App 内通话页面继续保留。
- 在 GitHub 仓库加入云端 Mac 构建配置。
- 使用 Codemagic 连接 GitHub 和 App Store Connect，完成自动签名与构建。
- 加入 Apple Developer Program 后，通过 TestFlight 安装和迭代。
- 根据“仅自用”或“未来上架”决定是否准备 App Store 审核材料。

完成标准：

- 不需要琳琳拥有 Mac；Windows 提交代码后能自动生成 TestFlight 新版本。
- 原生 App 能迁移 PWA 本地数据或提供清晰的搬家流程。
- Keychain、日历、提醒事项、HealthKit、后台音频和系统权限在 iPhone/iPad 真机通过验证。
- Apple Music 搜索、播放、队列和后台控制在真机稳定工作；断开授权或订阅不可用时不会破坏客厅其他功能。
- LRCLIB 歌词能够自动匹配并随播放时间滚动；匹配失败时正确降级，Ember 不会获取或编造不存在的歌词。
- HealthKit 桥接层只能读取已授权类型，代码和权限声明中均不存在健康数据写入能力。
- 大量 HealthKit 原始样本由本地代码整理，不进入模型上下文、不产生 Token 消耗。
- 睡眠整理结果能区分上床、入睡、醒来和离床；没有可靠数据时不得生成猜测结果。
- Apple 健康经期记录能正确进入 Ember Home 经期系统，重复同步不会产生重复周期。
- Ember 只能看到经过授权的健康摘要，不能查询整份 HealthKit 数据库。
- 主屏幕和锁屏小组件能正确显示宠物状态；一键喂食/摸摸不会重复执行。
- 小组件、App 与云端宠物状态能够处理延迟和冲突，不把旧状态覆盖到新状态上。
- Ember 带话和饥饿提醒遵守次数上限、安静时段和用户通知权限。
- PWA 继续保留为可用版本，原生打包不会成为唯一入口。

费用原则：

- PWA 开发阶段不购买 Apple Developer Program。
- 只有准备 TestFlight/原生分发时才开通会员；会员按年续费。

## 六、第一轮动工顺序

真正开始时只按以下顺序推进：

1. 获取并检查作为起点的北极星代码。
2. 确认许可证、框架和 iOS 打包路线。
3. 在 Windows 跑通原始项目。
4. 建立 Ember Home 新分支和最小首页。
5. 部署可安装的 PWA，并在 iPhone/iPad 添加到主屏幕。
6. 保证聊天室完整可用并固定对话式布局。
7. 接入 Ember 人格、现有对话记忆和 OmbreBrain。
8. 跑通一份北极星备份的迁移预览。
9. 实现分句发送、聊天室主题、作品索引、自然语言意图与上下文导航。
10. 建立客厅音乐角界面、音乐/歌词适配器与模拟联调。
11. 开始书房第一版。

在第 5 步 PWA 真机运行成功以前，不同时开发日历、观影、游戏和抖音。全部 PWA 计划功能竣工并通过 iPhone/iPad 整体验收后，再建立 Capacitor/iOS 原生工程，并处理签名、TestFlight、小组件和 App Store；这些工作不得与 PWA 功能开发并行提前开始。

## 九、开发环境与远程协作

Windows 第一阶段需要：

- ChatGPT/Codex Windows 桌面版。
- Node.js LTS。
- Git for Windows。
- Chrome 或 Edge。
- GitHub 账号；GitHub Desktop 和 VS Code 可选。

第一阶段不提前安装 Docker、本地大模型、Playwright、Python、Xcode 或 iOS 模拟器；项目真正需要时再逐项增加。

建议配置：

- 16GB 内存与 SSD 为推荐配置。
- 8GB 内存也能完成 PWA，但应减少同时运行的服务和浏览器标签。
- PWA 开发不需要独立显卡。
- 本地小模型、视频分析和大游戏 AI 玩家项目的硬件要求在各自阶段单独评估。

远程开发方式：

1. Windows 打开 ChatGPT/Codex 并保持开机、联网。
2. 使用 ChatGPT Remote 将 iPhone 与 Windows 配对。
3. 琳琳可以在手机上用语音输入向 Codex 下达开发指令、查看结果并批准操作。
4. 文件、Node.js、测试和浏览器预览实际运行在 Windows。
5. 需要 Windows 图形界面或 Chrome 自动化时，电脑保持解锁。

项目长期上下文必须写入仓库：

```text
ember-home/
├── AGENTS.md
└── docs/
    ├── product-spec.md
    ├── development-plan.md
    ├── architecture.md
    └── decisions/
```

- `AGENTS.md` 保存 Codex 每次必须遵守的项目规则。
- 产品需求、架构和重要决定写进 `docs/`，不依赖某一个聊天窗口长期记住全部讨论。
